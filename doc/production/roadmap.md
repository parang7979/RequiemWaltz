# 개발 순서와 출시 판단 기준

첫 목표는 석교에서 적을 공중에 띄워 무기를 바꿔 때리고, 착지하는 순간 돌가루가 잠깐 달빛을 받는 장면이다. 서로 다른 무기의 손맛과 어두운 화면의 판독성을 이 한 방에서 확인한 뒤 성의 구조를 늘린다. [게임 디자인 방향](../design/game-direction.md)

## 이번 설정의 범위

Godot 4.7.2와 GDScript로 시작한다. 초기 회랑과 석교는 이동·점프·착지, 착지 효과와 소리, 달빛 아래의 스프라이트를 확인하는 시험 공간이다. 적과 공격 판정, 무기 교체, 런 진행은 아래 단계에서 구현한다. 도구 연동의 첫 결과물은 캐릭터와 효과의 최종 품질을 결정하기 위한 샘플이다.

아래 기간은 1인이 전업으로 기획·코드·도트 보정·테스트까지 맡는다는 가정에서 잡은 **단계별 작업량의 초안**이다. 첫 전투실을 만든 뒤 공격 동작 하나, 적 하나, 배경 한 방에 실제 들어간 시간을 기록한다. 슬라이스 완료 후 그 실측치로 전체 구역 수와 출시 일정을 정한다. 외부 플러그인 이식, 작화 재작업, 기기별 성능 차이는 편차가 크다.

## 1. 기초 설정과 제작 실험 · 2~5작업일

**시작점**은 로컬 저장소, 사용할 엔진, 세 제작 도구다. 회랑에서 픽셀 배율, 카메라 이동, 발 위치와 접지 프레임을 맞춘다. 스프라이트 한 장을 좌우에서 비춰 노멀 방향을 보고, 광원이 움직일 때도 발광 부분이 의도한 자리에 남는지 본다. 착지 효과와 소리는 같은 접지 사건에서 재생한다.

**완료 판단**은 새 작업 복사본에서 캐시를 재생성한 뒤 기본 장면이 열리고, 좌우 이동과 점프 후 발판에 안정적으로 닿으며, 한 번의 착지에 효과와 소리가 한 번씩 나는 것이다. 생성 원본 한 개를 편집해 게임에서 변경된 결과도 볼 수 있어야 한다.

## 2. 첫 전투실 · 2~4주

**선행 조건**은 반복해서 진입할 수 있는 시험 공간과 안정적인 접지다. 첫 며칠에는 한 적의 준비·공격·회수, 피해와 재시작부터 만든다. 이어 지상 베기, 띄우기, 공중 추격, 무기 교체, 내려치기를 한 줄로 잇는다. 예시 무기는 짧은 회수 동작의 세검과 넓은 궤적의 대낫이다. 공격별 유효 시간과 맞은 위치를 화면에 표시해 판정과 작화의 어긋남을 찾는다.

**완료 판단**은 키보드와 패드로 각각 띄우기 → 추격 → 공중 교체 타격 → 착지를 재현하는 것이다. 명중과 헛침의 다음 입력이 설계대로 달라지고, 가장 밝은 타격 장면에서도 다른 적의 준비 자세를 알아볼 수 있어야 한다. 처음 해 보는 사람에게 짧게 맡겨 어느 입력에서 연계가 끊기는지, 무엇에 맞았다고 느끼는지 기록한다. 여기서 전투 동작과 카메라를 한 차례 고친 뒤 방 제작에 들어간다.

## 3. 10~15분짜리 소구역 · 추가 4~8주

**선행 조건**은 첫 전투실에서 성격이 다른 두 무기와 회피가 쓸 만하다는 플레이테스트 결과다. 허브, 아래 회랑, 능력 획득처, 되돌아오는 발코니, 마지막 강적을 한 구역으로 묶는다. 런마다 바뀌는 곁방은 두 배치부터 시작한다. 이 구역에만 바람이 전달되는 나뭇가지·풀, 얕은 물의 반사, 재방문 때 달라진 원경을 완성 수준으로 올린다. 대화 원화 한 장과 노멀맵으로 LiveIllustration 이식을 시험한다. 이식이 길어지면 같은 원화로 대화 흐름부터 테스트한다.

**완료 판단**은 처음 온 사람이 약 10~15분 동안 전투, 일시 강화 선택, 이동 능력 획득, 이전에 본 길의 개방과 마지막 전투를 경험하는 것이다. 사망하고 프로그램까지 재시작해도 영구 능력과 지름길이 이어지고, 두 가지 곁방 배치에서 모두 목적지에 닿아야 한다. 흑백 지도에서 귀환 경로를 찾게 하고, 가장 효과가 많은 전투 중 기준 Windows PC와 해상도를 기록해 60fps 목표의 프레임 시간 예산인 약 16.7ms를 반복해서 넘기는 구간을 찾고 고친다. 측정과 품질 확인은 독립 실행 빌드에서도 실시한다.

## 4. 알파와 Steam 데모

**선행 조건**은 슬라이스의 실측 제작비와 첫 사용자 테스트다. 다음 구역을 하나 더 만들어 측정한 속도가 유지되는지 본다. 그 결과로 본편의 구역·무기·보스 수를 정하고, 처음부터 엔딩까지 한 번 이어지는 알파를 만든다. 데모에는 완성도가 가장 높은 소구역을 사용한다. 패드만으로 새 게임, 일시정지, 맵, 설정, 종료까지 진행하고 키보드에서도 같은 기능에 접근할 수 있게 한다.

**완료 판단**은 알파에서 새 저장으로 엔딩까지 도달하고, 데모는 독립 설치 환경에서 시작부터 마지막 전투와 종료 화면까지 진행하는 것이다. 동일한 실패가 누적되는 지점은 입력 실패·공격 예고·길 찾기로 나눠 한 차례 개선한다. 데모와 본편의 저장 파일 정책을 정하고 둘을 같은 PC에서 실행해 진행 손실이 없는지 확인한다.

## 5. 출시 준비

**선행 조건**은 Windows 배포 빌드, 게임과 일치하는 상점 이미지, 출시할 콘텐츠 목록이다. 최초 설치, 기존 버전 업데이트, 패드 재연결, 저장 직후 종료·재실행을 시험한다. 최종 후보 빌드의 커밋과 배포 버전을 기록하고, 동일 버전이 Steam에서 설치·실행되는지 확인한다. 본편의 저장·진행 차단 오류를 해결하고 상점 페이지와 빌드 심사를 마친 시점에 공개일을 확정한다. [Steamworks 심사 절차](https://partner.steamgames.com/doc/store/review_process) · [Steamworks 출시 절차](https://partner.steamgames.com/doc/store/releasing)

### 배포에 필요한 준비

- **Windows.** 프로젝트 엔진 버전에 맞는 Export Templates를 준비하고 `Windows Desktop` 프리셋에서 x86_64 릴리스 빌드를 만든다. 내보낸 `.exe`와 함께 출력된 `.pck` 등 배포 파일을 한 폴더에 모은다. Godot와 제작 도구가 설치되지 않은 Windows 환경에서 장면 전환·음원·입력·저장을 확인한다. [Godot 프로젝트 내보내기](https://docs.godotengine.org/en/stable/tutorials/export/exporting_projects.html) · [Windows 내보내기](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_windows.html)
- **GitHub.** 원격 저장소를 정하는 시점까지 로컬 Git 이력을 쌓는다. 소유자와 공개 범위를 정한 뒤 README 등으로 초기화하지 않은 빈 저장소를 만들고 `git remote add origin <저장소-URL>`, `git remote -v`, `git push -u origin main` 순서로 연결한다. 별도 폴더에 새로 받아 기준 장면이 열리는지 확인한다. [GitHub의 기존 로컬 저장소 연결 절차](https://docs.github.com/en/migrations/importing-source-code/using-the-command-line-to-import-source-code/adding-locally-hosted-code-to-github?platform=windows)
- **Steam 데모.** Steamworks에서 본편에 연결된 별도 데모 App ID와 디포를 설정한다. 데모에 실제 포함한 장면으로 상점 자료를 만들고 데모 체크리스트에 따라 페이지와 빌드 심사를 진행한다. 본편보다 먼저 배포할 때는 본편의 출시 예정 페이지도 공개한다. [Steamworks 데모 문서](https://partner.steamgames.com/doc/store/application/demos)
- **생성 배경과 Content Survey.** AI로 생성한 원경을 도트화해 게임에 싣는다면, 플레이어가 보는 최종 배경을 만드는 데 AI를 사용한 경위를 `Pre-Generated` 항목에 설명한다. 배경별 원본·생성 도구·도트 보정 과정·사용 권한 근거를 제작 중에 기록해 실제 데모 및 본편의 내용과 대조한다. SpriteKiln·PixelFX·PlinkFX는 각 자산의 실제 제작 방식에 따라 기록한다. Steamworks는 개발 중 생성한 콘텐츠와 게임 실행 중 AI가 생성하는 콘텐츠를 구분한다. [Steamworks Content Survey](https://partner.steamgames.com/doc/gettingstarted/contentsurvey)

## 일정이 밀릴 때 줄일 순서

1. 첫 구역의 핵심 전망 한 곳과 접지 반응을 살리고 구역별로 서로 다른 수면 반사, 날씨 조합, 원경 변화의 **종류**를 줄인다.
2. 대화 원화 한 장에 방향 조명을 완성한 뒤 추가 인물·포즈·표정과 플러그인 편집기 확장을 미룬다.
3. 두 무기의 역할을 유지하면서 세 번째 이후의 무기, 무기별 고유 처치 연출, 드문 강화끼리의 특수 조합을 줄인다.
4. 추가 바이옴과 보스의 수를 조정한다. 남는 각 구역에는 능력을 얻은 뒤 돌아갈 장소, 다른 경로를 고를 이유, 적의 다음 수를 읽는 전투를 한 번씩 담는다.

무엇을 줄였든 다음 플레이테스트에서 공중 무기 교체, 공격 예고의 가독성, 접지감, 사망 후 다시 열리는 탐험 선택을 재확인한다. 이 네 가지가 흔들리면 새 구역을 추가하기 전에 해당 장면을 수정한다.
